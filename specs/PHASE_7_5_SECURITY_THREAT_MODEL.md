## 1. Security Concepts & Boundary Clarifications

To prevent false security assumptions, this threat model explicitly differentiates five core security properties:

| Security Property | Operational Definition in this Platform | Mathematical / Architectural Mechanism |
|---|---|---|
| **Cryptographic Integrity** | The mathematical certainty that stored bytes have not been modified, corrupted, or reordered since computation. | SHA-256 hash chaining over RFC 8785 canonical JSON; Merkle roots; checkpoint digests. |
| **Authenticity** | The certainty that an audit event or checkpoint was generated by the legitimate application and not an unauthorized actor. | Bearer token authentication on HTTP endpoints; Windows DPAPI-backed Ed25519 or HMAC signature over checkpoint digest. |
| **Availability** | The ability of authorized analysts and services to query audit records and verify chains on demand. | Loopback binding; SQLite WAL multi-reader concurrency; bounded batch execution preventing database locks. |
| **Immutability** | Physical impossibility of overwriting or deleting stored data once written. | **NOT achievable on local standard filesystems.** Immutability requires hardware WORM drives or cloud Object Lock. On local NTFS, write permissions allow modification. |
| **Non-Repudiation** | Inability of the author of an action to deny having performed it, provable to an independent third party. | Achieved for normal users via audit chaining and DPAPI signing. **Limited against local administrators** unless an external trust anchor (e.g. remote syslog or offline ledger) is active. |

## 2. Threat Analysis Matrix (18 Threat Vectors)

---

### Threat 1: Event Modification (Tampering with Existing Row)
- **Preconditions:** Attacker has direct write access to `siem_history.db` or executes an arbitrary SQL injection vulnerability.
- **Impact:** Attacker alters an audit record (e.g. changing `action`, `actor_id`, `outcome`, or `timestamp`) to conceal unauthorized actions.
- **Detection Method:** `verify_chain_integrity()` or `VerifySuffix()` recomputes canonical SHA-256 for event $i$. Recomputed hash will not match stored `event_hash`, reporting `TAMPER_DETECTED`. If the attacker also modifies `event_hash`, event $i+1$'s `previous_hash` check fails with `PREDECESSOR_MISMATCH`.
- **Mitigations:** 100% parameterized SQLAlchemy queries (zero raw SQL); NTFS ACLs restricting database file to application user; SHA-256 hash chaining.
- **Residual Risk:** An attacker who has local administrator access can recompute all subsequent hashes forward to the active tip.
- **Status:** **ADDRESSED** (Cryptographic integrity guaranteed; local admin limitation documented in ADR-012/ADR-013).

---

### Threat 2: Event Deletion (Selective Middle-Record Pruning)
- **Preconditions:** Attacker deletes a specific incriminating audit event from `audit_events`.
- **Impact:** Gaps in historical timeline; concealment of specific investigations or administrative sweeps.
- **Detection Method:** When event $i$ is deleted, event $i+1$'s `previous_hash` still references event $i$'s `event_hash`, but event $i-1$'s hash is present. Verification halts with `PREDECESSOR_MISMATCH`.
- **Mitigations:** Sequential hash chaining; no public or internal API endpoints support deleting individual audit rows.
- **Residual Risk:** Local admin can bridge the gap by updating event $i+1$'s `previous_hash` and re-chaining forward.
- **Status:** **ADDRESSED**.

---

### Threat 3: Event Insertion (Fabrication of Historical Events)
- **Preconditions:** Attacker attempts to inject a fictitious audit event into the middle of the historical timeline.
- **Impact:** Falsification of evidence or framing of benign analyst accounts.
- **Detection Method:** Inserting event $e_{\text{new}}$ between $e_{i}$ and $e_{i+1}$ requires $e_{\text{new}}.\text{previous\_hash} == e_i.\text{event\_hash}$, but $e_{i+1}.\text{previous\_hash}$ still points to $e_i$. Verification detects `PREDECESSOR_MISMATCH` at $e_{i+1}$.
- **Mitigations:** Strict sequential hashing; `AuditEvent` insert path only accessible through internal `AuditRepository.log_event()`.
- **Residual Risk:** Admin re-chaining forward from insertion point.
- **Status:** **ADDRESSED**.

---

### Threat 4: Event Reordering (Timestamp or Sequence Swapping)
- **Preconditions:** Attacker reorders rows in the database to misrepresent the chronological sequence of events.
- **Impact:** Misleading timeline analysis during forensic incident reconstruction.
- **Detection Method:** Verification queries records strictly ordered by `timestamp ASC, audit_id ASC`. Any swapping causes immediate `PREDECESSOR_MISMATCH` and `ORDERING_VIOLATION`.
- **Mitigations:** Deterministic query ordering; hash inclusion of timestamp and audit_id.
- **Residual Risk:** Low.
- **Status:** **ADDRESSED**.

---

### Threat 5: Chain Truncation (Deleting the Active Tail)
- **Preconditions:** Attacker deletes the most recent $k$ records from the end of `audit_events`.
- **Impact:** Conceals the most recent malicious activity.
- **Detection Method:** A simple internal verifier cannot detect tail truncation unless a **tail digest is anchored externally** (e.g. published to Windows Event Log, analyst console, or external witness).
- **Mitigations:** Periodic checkpoint generation; logging checkpoint digests to stdout/application log; optional external trust anchoring.
- **Residual Risk:** In the absence of an external witness or recent checkpoint, the very latest uncheckpointed tail can be truncated by a local file owner.
- **Status:** **PARTIALLY ADDRESSED** (Fully addressed once checkpointed; active tail protected via operational logs).

---

### Threat 6: Checkpoint Replacement (Forging a Bogus Anchor)
- **Preconditions:** Attacker replaces an active checkpoint in `audit_checkpoints` with a fabricated checkpoint that matches an altered history.
- **Impact:** Attacker successfully covers up modified historical records.
- **Detection Method:** 
  1. Checkpoint Meta-Chain check: Checkpoint $m$ must link to Checkpoint $m-1$'s `checkpoint_digest`. Fabricating $m$ breaks the link to $m-1$ or requires rewriting all prior checkpoints back to sequence 1.
  2. With Windows DPAPI signing enabled (`HMAC-SHA256` or `ED25519`), the replacement checkpoint fails signature verification (`CHECKPOINT_SIGNATURE_INVALID`).
- **Mitigations:** Monotonic checkpoint sequencing; checkpoint meta-chaining; DPAPI cryptographic signatures.
- **Residual Risk:** An attacker with local administrator privileges can call `CryptUnprotectData`, obtain the signing key, and sign a forged checkpoint.
- **Status:** **ADDRESSED**.

---

### Threat 7: Checkpoint Rollback (Reverting to an Older Valid Checkpoint)
- **Preconditions:** Attacker drops recent checkpoints and replaces the active pointer with an older, authentic checkpoint.
- **Impact:** Causes the verifier to expect an older state, potentially allowing re-introduction of purged records or confusing retention boundaries.
- **Detection Method:** The verifier detects a sequence regression (`checkpoint_sequence` $< \text{expected}$) or detects that the earliest live event's `previous_hash` does not match the older checkpoint's `last_included_event_hash` (`UNVERIFIED_GAP_DETECTED`).
- **Mitigations:** Monotonic sequence validation; strict boundary anchoring (`first_event.previous_hash == CP.last_included_event_hash`).
- **Residual Risk:** None; boundary check strictly prevents mismatch.
- **Status:** **ADDRESSED**.

---

### Threat 8: Signing-Key Compromise (Windows DPAPI Trust Analysis)
- **Preconditions:** Attacker gains code execution on the host machine.
- **Impact:** Attacker extracts the signing key and forges valid checkpoint signatures.
- **Detection Method:** Host OS audit logs tracking process injection, memory scraping, or unauthorized access to user profile stores.
- **Mitigations:** 
  1. The raw signing secret is **never stored in plaintext** in `.env`, configuration files, or database rows.
  2. The key is encrypted via Windows DPAPI (`CryptProtectData`) under Current User or Local Machine scope.
  3. Non-administrative users and external processes cannot decrypt the key blob.
- **Residual Risk:** Any process executing as `NT AUTHORITY\SYSTEM` or running under the user's interactive Windows login session can call `CryptUnprotectData` and recover the raw signing secret. **DPAPI provides OS-level user isolation, not kernel-level administrator isolation.**
- **Status:** **ADDRESSED TO THE LIMIT OF HOST OS CAPABILITIES** (Formally documented in ADR-013).

---

### Threat 9: Local Administrator / Filesystem Compromise
- **Preconditions:** Malicious insider or malware obtains local Administrator rights on the Windows host.
- **Impact:** Complete ability to overwrite SQLite files, delete archives, recompute hashes, invoke DPAPI, and forge local logs.
- **Detection Method:** Local software cannot reliably detect its own subversion when the OS kernel/admin is hostile.
- **Mitigations:** 
  - Formal acknowledgment in ADR-012, ADR-013, and PRD Section 5.3.
  - Operational guidance: in high-threat enterprise deployments, checkpoint digests must be published to a **separately controlled external trust anchor** (e.g. remote syslog server, WORM storage, or external witness ledger) that the local Windows administrator cannot alter.
- **Residual Risk:** Recognized as an inherent boundary of local, loopback-only single-host software.
- **Status:** **OUT OF SCOPE FOR SOFTWARE-ONLY LOCAL DEPLOYMENT** (Documented boundary).

---

### Threat 10: SQLite Database Corruption
- **Preconditions:** Hardware malfunction, unclean shutdown, or sudden power loss during write operations.
- **Impact:** SQLite B-Tree corruption or malformed pages in `siem_history.db`.
- **Detection Method:** `PRAGMA integrity_check` fails; SQLite throws `sqlite3.DatabaseError` on query.
- **Mitigations:** SQLite WAL mode with `PRAGMA synchronous = NORMAL`; automated foreign key enforcement; transactional integrity rollback.
- **Residual Risk:** Unrecoverable physical disk platter failure requires backup restoration.
- **Status:** **ADDRESSED**.

---

### Threat 11: WAL Recovery Failure
- **Preconditions:** Process killed while WAL has uncommitted transactions; `-wal` or `-shm` file deleted by operator.
- **Impact:** Loss of recent transactions or database locked in recovery mode.
- **Detection Method:** Backend startup fails during database engine initialization.
- **Mitigations:** Explicit warning in operational documentation: **Never manually delete WAL files**; use `PRAGMA wal_checkpoint(PASSIVE)` during maintenance.
- **Residual Risk:** Operator error manually deleting `-wal` files.
- **Status:** **ADDRESSED**.

---

### Threat 12: Clock Skew and Timestamp Manipulation
- **Preconditions:** Attacker or drifting host clock changes system time backwards or forwards.
- **Impact:** Retention pruning executes prematurely (if clock moves forward) or fails to prune (if clock moves backward); audit events inserted with out-of-order timestamps.
- **Detection Method:** Checkpoint protocol enforces `interval_end_timestamp >= interval_start_timestamp`; verifier detects events where timestamp regresses relative to sequence ID.
- **Mitigations:** All timestamps enforced in UTC with microsecond precision; monotonic ordering via `(timestamp ASC, audit_id ASC)`.
- **Residual Risk:** Virtual machine host clock jumps.
- **Status:** **ADDRESSED**.

---

### Threat 13: Concurrent Audit Writes (Fork / Race Conditions)
- **Preconditions:** Multiple concurrent API requests attempt to log audit events simultaneously.
- **Impact:** Two events read the same `latest_hash`, causing a branch or fork in the linear hash chain.
- **Detection Method:** Verification detects two events sharing the same `previous_hash` or broken sequential links.
- **Mitigations:** In `AuditRepository.log_event()`, `await session.flush()` forces the record into the database transaction immediately; SQLite single-writer serialization ensures sequential transaction commit.
- **Residual Risk:** Low.
- **Status:** **ADDRESSED**.

---

### Threat 14: Partial Transaction or Process Crash during Cleanup
- **Preconditions:** Power loss or SIGKILL occurs while `prune_expired_audit_events()` is halfway through deleting records.
- **Impact:** Inconsistent state where some records are deleted but no checkpoint is recorded, breaking the hash chain.
- **Detection Method:** Suffix verification fails with `UNVERIFIED_GAP_DETECTED`.
- **Mitigations:** **Atomic Transaction Contract:** Checkpoint insertion and event deletion occur strictly inside a single `BEGIN IMMEDIATE ... COMMIT` block. SQLite WAL rolls back uncommitted deletes automatically upon crash recovery.
- **Residual Risk:** None under standard ACID WAL semantics.
- **Status:** **ADDRESSED**.

---

### Threat 15: Loss or Corruption of Archived Data Files
- **Preconditions:** Offline archive file (`audit_archive_seq1.json.gz`) is deleted, moved, or bit-rotted on the filesystem.
- **Impact:** Operational database remains intact, but historical events cannot be audited.
- **Detection Method:** `VerifyArchive()` calculates physical file SHA-256 and compares against `audit_checkpoints.archive_sha256`, reporting `ARCHIVE_FILE_TAMPERED` or `ARCHIVE_FILE_MISSING`.
- **Mitigations:** Archive file SHA-256 digest is permanently preserved inside the database checkpoint row; operator alerts generated if archive cannot be read.
- **Residual Risk:** Physical data loss if no off-host backups exist.
- **Status:** **ADDRESSED**.

---

### Threat 16: Verification Code Defects (Bypass Bugs)
- **Preconditions:** Bug in `verify_chain_integrity()` returns `True` despite errors or skips checking key fields.
- **Impact:** Silent acceptance of tampered audit logs.
- **Detection Method:** Comprehensive unit and integration test suite with negative test cases (tampered hashes, missing rows, corrupted checkpoints).
- **Mitigations:** Strict fail-closed design; independent test assertions simulating all error modes; zero silent try/except passes.
- **Residual Risk:** Software regression risk mitigated by automated CI/CD test gates.
- **Status:** **ADDRESSED**.

---

### Threat 17: Retention-Policy Abuse / Accidental Evidence Destruction
- **Preconditions:** Operator or script invokes cleanup with an excessively short retention window (e.g. 1 day instead of 365 days).
- **Impact:** Active, forensically vital investigation and audit records are permanently erased.
- **Detection Method:** Pre-execution validation check asserts `retention_days >= 365` for audits and `retention_days >= 90` for investigations.
- **Mitigations:** Hard floor constants in backend configuration (`MIN_AUDIT_RETENTION_DAYS = 365`); cleanup defaults to `dry_run=True`; automated deletion disabled on startup.
- **Residual Risk:** None.
- **Status:** **ADDRESSED**.

---

### Threat 18: Archive Path Traversal & Unsafe Destination Injection
- **Preconditions:** Operator or configuration injector provides malicious path for `AUDIT_ARCHIVE_DIR` (e.g. `../../../../Windows/System32` or `C:\ sensitive\`).
- **Impact:** Arbitrary file overwrite or unauthorized access to sensitive filesystem locations.
- **Detection Method:** Path resolution validation asserts destination is within authorized directories and resolves absolute canonical paths.
- **Mitigations:** Strict path normalization; rejection of relative traversal tokens (`..`); NTFS permission checks ensuring the directory is owned by the application service account.
- **Residual Risk:** None.
- **Status:** **ADDRESSED**.
